# M1.39 — Attachment integrity verification

M1.39 adds explicit local integrity verification for persistent field-note attachments.

## Verification

Each M1.38+ attachment sidecar records the SHA-256 calculated from the stored bytes at creation or restore time. Integrity verification reads the sidecar and binary file independently and compares the recorded digest with a freshly calculated SHA-256.

Statuses are:

- `ok` — recorded and current SHA-256 match.
- `mismatch` — the binary file exists but its current SHA-256 differs from the recorded digest.
- `missing` — metadata exists but the binary file is missing.
- `unrecorded` — a legacy attachment has no recorded SHA-256 baseline; its current digest is reported but cannot be compared historically.

Verification is read-only. It never repairs, rewrites or deletes attachment data.

## API

- `GET /api/field-notes/{id}/attachments/integrity` verifies attachments for one existing field note.
- `GET /api/field-note-attachments/integrity` verifies attachments belonging to all current field notes.

Reports include generation time, totals for each status, attachment/note IDs, filename, expected digest, actual digest and current size when available.

## UI

The Attachment integrity tool can run a full local verification and download the resulting report as JSON. A non-zero mismatch or missing count is surfaced as an integrity problem.

## Compatibility and privacy

No field-note schema changes are introduced. Existing M1.36/M1.37 attachments without a persisted SHA-256 remain readable and are reported as `unrecorded`. All verification is local under `/data`; no checksum, filename or attachment content is sent to an external service.
